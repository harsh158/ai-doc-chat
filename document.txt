IAM Use Cases
Functional Requirements Presentation: Comprehensive overview of 37 identity and access management use

Identity Aggregation Full Load
Use Case No.
Use Case Priority
1
Must
Actors System
Goal
All user updates in authoritative HR application are synchronized with identities in Tuebora and downstream 
applications
Pre-Conditions Tuebora IAM application is up and running
Connectivity to target applications is up and running
Post-Conditions All user identities in Tuebora and downstream applications are accurately updated, 
created, or terminated based on the latest HR records from Darwinbox.
Activities Full load from Darwinbox collected and user records are aggregated 1.
All identities co-related between Tuebora and Full load entries are updated based 
on Employee ID
2.
Any new identities created in HR – Joiner process is triggered 3.
Any identities terminated – Leaver Process is triggered 4.
Any identity updated – Mover process is triggered 5.
Success/failure emails sent to configured DL 6.
Possible Errors Connectivity failures to Darwinbox or target applications.
Invalid data format or missing required attributes in Darwinbox.
Failure to co-relate identities between systems due to mismatched Employee IDs.
Errors during joiner, leaver, or mover process triggering in downstream systems.
Issues sending success/failure notifications.

Accounts and Access Aggregation
Use Case No.
Use Case Priority
3
Must
Actors System
Goal
Scheduled collection of accounts and access data, detection of unapproved access and alerting appropriate 
stakeholders
Pre-Conditions Target applications (Slack, Zoom, Google Workspace, Automic Work) are integrated 
via direct SCIM connectors.
Tuebora IAM application is up and running.
Connectivity to target applications is established and maintained.
Post-Conditions Accounts and access data collected from each application and Tuebora repository 
updated.
New accounts or access granted outside Tuebora generate unapproved access 
alerts for managers.
Accounts linked with Identities based on linking rules (Email Address).
Unlinked records shown as orphan accounts.
Accesses tagged per governance specification for privileged, risk category, 
account type.
Activities Scheduled aggregation process initiates collection of accounts and access data 
from integrated applications.
1.
Each application's account and access data is processed and updated within the 
Tuebora repository.
2.
Unapproved access instances (created outside Tuebora) are identified and trigger 
alerts to relevant managers.
3.
Identities are linked to accounts using defined linking rules, primarily email 
addresses.
4.
Accounts without corresponding identities are flagged as orphan accounts for 
review.
5.
All collected accesses are categorized and tagged according to governance 
specifications (e.g., privileged, risk level, account type).
6.
Possible Errors Connection failure to target applications during scheduled aggregation.
Data inconsistencies or corruption during data collection and update.
Incorrect linking of accounts to identities due to faulty linking rules.
Failure to detect or alert on unapproved access.
Inaccurate tagging of accesses according to governance specifications.
Performance issues leading to delayed data aggregation or alerting.

Leaver Process
Use Case No.
Use Case Priority
13
Must
Actors System
Goal
De-provision the account from IAM and all downstream systems and ensure no access is available to the 
user after the last working date
Pre-Conditions Employee's last working date is confirmed in HR system.
Termination reason and type are recorded in HR system.
Post-Conditions Profile is disabled in Tuebora on last working date or immediately in case of 
immediate terminations
GoogleWorkspace/Zoom/Slack/AtomicWork accounts disabled after last working 
date has passed
All application access is revoked on Date_of_exit+1 UTC time
Activities Termination Initiated: HR initiates the termination process and sets the last working 
date in DarwinBox.
1.
Reason Computation: System computes the termination reason (e.g., resignation, 
abscond) based on HR data.
2.
De-provisioning Trigger: On the last working date, de-provisioning is triggered in 
IAM (Tuebora).
3.
System De-activation: User accounts are disabled and access is revoked across 
all connected downstream systems.
4.
Possible Errors Access not fully revoked from all downstream systems.
Accounts de-provisioned before the last working date.
User data not handled according to compliance policies (e.g., deletion or archival).
Synchronization failures leading to orphaned accounts.
